# 🍪 Кекс-Фабрика

**P2P gossip систем за откривање активних чворова** у замишљеној фабрици кекса — без централног сервера.

Сваки чвор (станица на производној линији) води локални списак чланова мреже, периодично га размењује са насумичним суседима, открива оне који су престали да „куцају" и допушта новим станицама да се придруже преко једног познатог чвора (seed). Ако пећница стане, суседне станице то сазнају за неколико секунди; кад се нова станица укључи, линија то аутоматски види.

|              |                                                              |
| ------------ | ------------------------------------------------------------ |
| Језик        | C11, POSIX сокети                                            |
| Транспорт    | UDP (IPv4)                                                   |
| Платформа    | Linux                                                        |
| Модел        | један процес = један чвор, једнонитна петља вођена `poll()`-ом |
| Спецификација | [`docs/SPEC.pdf`](docs/SPEC.pdf) (званични извор) — ово је њен радни извод |

> 🚧 **Статус:** пројекат је у почетној фази. Команде из „Брзог почетка" постају доступне како се затварају задаци — прати [Milestones](../../milestones) и [Roadmap](../../issues?q=is%3Aissue+Roadmap).

## Шта систем ради

Сваки чвор:

- има јединствен `node_id`, IP, порт и **улогу**;
- се придружује слањем `MSG_JOIN` једном познатом чвору (seed);
- сваких `T_GOSSIP` повећава сопствени heartbeat и шаље свој списак до `FANOUT` насумичних суседа (push); прималац одговара својим (pull);
- означава чвор као `SUSPECT`, па `DEAD`, ако му heartbeat не напредује; `DEAD` записе после неког времена брише;
- при излазу шаље `MSG_LEAVE`; при рестарту са истим ID-ем бива поново прихваћен (нова инкарнација).

Станице су равноправне — не постоји „главни рачунар". Машине се симулирају (нема правог рада производних машина).

| Улога          | Станица         | Шта симулира                          |
| -------------- | --------------- | ------------------------------------- |
| `ROLE_MIXER`   | Мешалица        | замес теста, периодично „завршава шаржу" |
| `ROLE_ROLLER`  | Ваљак           | ваљање теста у траке                  |
| `ROLE_CUTTER`  | Секач           | сечење облика кекса                   |
| `ROLE_OVEN`    | Пећница         | печење (најкритичнија станица)        |
| `ROLE_COOLER`  | Хладњак         | хлађење                               |
| `ROLE_PACKER`  | Паковање        | пакује кекс у кутије                  |
| `ROLE_MONITOR` | Контролна соба  | само посматра, исписује стање линије  |

## Брзи почетак

Потребно: `gcc` (C11), `make`, Linux. Опционо: `tmux` (демо), `valgrind`, `cppcheck` (провера квалитета).

```bash
make                 # → ./biscuitd
make test            # јединични тестови
make debug           # ./biscuitd-debug са -fsanitize=address,undefined
make itest           # интеграциони сценарији S1–S8 (дуго траје)
make clean
```

Два чвора на једној машини:

```bash
./biscuitd --id 1 --role mixer --bind 127.0.0.1:9001
./biscuitd --id 2 --role oven  --bind 127.0.0.1:9002 --seed 127.0.0.1:9001
```

Цела линија (7 станица), или произвољан број чворова:

```bash
scripts/run_factory.sh start          # 7 станица, свака зна само seed (чвор 1)
scripts/cluster.sh send 2 list        # команда чвору 2
scripts/run_factory.sh stop
```

Команде у процесу (stdin): `list`, `stats`, `fail`, `recover`, `leave`, `quit`, `help`.

> Спецификација има `main.c` као „аргументи + CLI". Ми га делимо на `main.c` (аргументи, покретање) и `cli.c` (команде) да двоје могу да раде паралелно без сукоба. `node.h` и `cli.h` су додатак спецификацији.

**Правило слојева:** `gossip`, `failure` и `cli` користе `membership`; сви пишу на мрежу само преко `node_send()`; једино `net` и `node` дирају сокет. Нема динамичке алокације у главној петљи (статичке табеле).

**Кључно правило о времену:** `last_update_ms` је *локално* монотоно време (`CLOCK_MONOTONIC`) и **никад** се не пореди са туђим часовником. Показатељ напретка је само чињеница да је пар `(incarnation, heartbeat)` порастао; време те чињенице мери локални часовник.

## Протокол

Све вишебајтне вредности су у network byte order. Једна порука = један UDP датаграм ≤ 1400 B. Структуре се **никад** не шаљу директно — кодира се поље по поље.

**Заглавље (12 B):**

| Поље        | B | Опис                                       |
| ----------- | - | ------------------------------------------ |
| `magic`     | 2 | `0x4B58` („KX")                            |
| `version`   | 1 | `1`                                        |
| `type`      | 1 | тип поруке (види доле)                     |
| `sender_id` | 4 | ID пошиљаоца                               |
| `count`     | 2 | број записа који следе (≤ 32)              |
| `reserved`  | 2 | `0` (на пријему се игнорише)               |

**Запис о чвору (20 B):** `node_id`(4) · `ip`(4) · `port`(2) · `role`(1) · `state`(1) · `incarnation`(4) · `heartbeat`(4).

Највећа порука: 12 + 32·20 = **652 B**. Декодер проверава `magic`, `version`, `count ≤ MAX_ENTRIES_MSG` и да је дужина **тачно** `12 + count·20`; све што не прође тихо се одбацује и броји у статистици.

| Тип (вредност)       | Смер              | Садржај                          |
| -------------------- | ----------------- | -------------------------------- |
| `MSG_JOIN` (1)       | нови → seed       | 1 запис (сам чвор)               |
| `MSG_GOSSIP` (2)     | A → B             | сопствени запис + узорак (push)  |
| `MSG_GOSSIP_REPLY` (3)| B → A            | списак који B има (pull)         |
| `MSG_LEAVE` (4)      | излазни → суседи  | 1 запис са `STATE_LEFT`          |

## Алгоритам

**Gossip рунда** (сваких `T_GOSSIP`): `self.heartbeat++`; од чланова у стању `ALIVE`/`SUSPECT` (без себе) изабери до `FANOUT` насумичних без понављања; свакоме пошаљи `MSG_GOSSIP` са својим записом и узорком табеле.

**Merge** (упоређивање је лексикографско — прво инкарнација, па heartbeat): рестартовани чвор (већа инкарнација) надјача стару `DEAD` ознаку, а закаснела порука са старим heartbeat-ом не може да „оживи" пали чвор. Прецизна правила: [Д3](#договори-одлуке-пре-кодирања).

**Детектор испада** (мери се само локално `now - last_update_ms`):

```
ALIVE   --(тишина > T_SUSPECT)-->  SUSPECT
SUSPECT --(тишина > T_FAIL)----->  DEAD
SUSPECT --(стиже већи heartbeat)->  ALIVE
DEAD    --(тишина > T_CLEANUP)-->  [уклоњен]
DEAD    --(стиже већа инкарнација)-> ALIVE
```

`DEAD` се задржава као „надгробни споменик" (tombstone) да неки други чвор са старим записом не би вратио мртвог члана у наш списак.

**Подразумевани параметри** (подесиви): `T_GOSSIP = 1 s`, `FANOUT = 3`, `T_SUSPECT = 5 s`, `T_FAIL = 10 s`, `T_CLEANUP = 30 s`.

**Очекивана конвергенција:** ≈ `log_k(N) + c` рунди; за N = 32, k = 3 то је 4–6 рунди (≈ 5 s). Проверава се мерењима ([#20](../../issues)).

## Конфигурација и CLI

```bash
./biscuitd --id 3 --role oven --bind 127.0.0.1:9003 --seed 127.0.0.1:9001 \
  [--gossip-ms 1000] [--fanout 3] [--suspect-ms 5000] \
  [--fail-ms 10000] [--cleanup-ms 30000] [--loss 0.0] [--verbose]
```

`--loss p` (0.0–1.0) симулира губитак датаграма при слању — за тестове.

Излаз `list` (формат је **уговор**, види Д16; скрипте га парсирају):

```
ID  ROLE    ADDR             STATE    HB   SILENCE
1   MIXER   127.0.0.1:9001   ALIVE    42   0.3s
2   ROLLER  127.0.0.1:9002   ALIVE    41   0.8s
3   OVEN    127.0.0.1:9003   SUSPECT  37   6.1s
# total=3 alive=2 suspect=1 dead=0 left=0
```

Излаз `stats` су редови `кључ вредност`, последњи ред је `# end`. `fail` „замрзава" слање (симулација пада), `recover` враћа рад, `leave` уредно излази, `quit` излази без `LEAVE`-а.

## Договори (одлуке пре кодирања)

Спецификација на неколико места није јасна или је непотпуна. Ово су одлуке донете **унапред** да Dev A и Dev B граде против истог уговора. Ако се са неком не слажеш — отвори issue са ознаком `spec-clarification` *пре* него што крене имплементација, и измени овај одељак у истом PR-у.

| #   | Одлука |
| --- | ------ |
| Д1  | `self` је **одвојен** од `table[]`. Табела садржи само остале чланове (капацитет `MAX_NODES - 1`, тј. укупно до 64 чвора са собом). „Поглед на мрежу" (`list`, узорак за слање) = `self` + `table`. |
| Д2  | ID seed-а је при старту **непознат** (`--seed` даје само адресу). Адреса се чува у `node_t`; seed улази у табелу тек кад стигне његов одговор (његов запис је у `MSG_GOSSIP_REPLY`). Ово одступа од §7.4 („у табелу уписује себе и seed"). |
| Д3  | **Merge правила** (`e` = примљени запис, `m` = наш запис). (1) `e.node_id == self` → игнориши. (2) Нема `m` → додај; стање је `DEAD`/`LEFT` ако је `e` такав, иначе `ALIVE`. (3) `(e.inc, e.hb) > (m.inc, m.hb)` → *напредак*: ако је `m` `DEAD`/`LEFT` са **истом** инкарнацијом → игнориши (терминално стање); иначе копирај `inc/hb/role/ip/port`, стање = `LEFT` ако је `e.state == LEFT`, иначе `ALIVE`, `last_update = now`. (4) Иста инкарнација и `e.state == LEFT` → `m.state = LEFT`. (5) Иначе игнориши. `SUSPECT` је **искључиво локална процена** — никад се не преузима са мреже; стање `e` (осим `LEFT`) се за већ познате чланове игнорише. *(Псеудокод из §7.2 са `m = e` би преузео и туђе `SUSPECT`/`DEAD`; зато је прецизиран.)* |
| Д4  | `DEAD` се брише кад `now - last_update > T_CLEANUP` (од последњег напретка). `LEFT`: при преласку у `LEFT` поставља се `last_update = now`, па се брише после `T_CLEANUP` од тог тренутка. |
| Д5  | Инкарнација = `time(NULL)` (секунде) при старту. Познато ограничење: рестарт у истој секунди даје исту инкарнацију. |
| Д6  | На `MSG_GOSSIP` и `MSG_JOIN` одговара се са `MSG_GOSSIP_REPLY`. На `MSG_GOSSIP_REPLY` и `MSG_LEAVE` **не** одговара се (нема ping-pong-а). Одговор иде на изворну адресу датаграма. |
| Д7  | Wire детаљи које спец. не прописује: бројеви типова (види табелу); `ip` на жици су 4 бајта у network order-у (као `in_addr`), `port` је `htons`; `last_update_ms` **не** иде на жицу (после декодирања је `0`, поставља га пријем). `JOIN` и `LEAVE` имају тачно 1 запис и `entries[0].node_id == sender_id`; `LEAVE` носи `STATE_LEFT`. Неважећи `role` (> 6) или `state` (> 3) или `port == 0` → порука се одбацује. |
| Д8  | `--bind` мора бити конкретна IPv4 адреса (не `0.0.0.0`) јер се објављује у записима. UDP сокет се **не** отвара са `SO_REUSEADDR` (није потребан за брз рестарт, а омогућио би два чвора на истом порту). |
| Д9  | `stdout` = **само** излаз CLI команди; сви логови иду на `stderr`. Сав излаз програма (логови, поруке, имена стања) је на енглеском; документација на српском. EOF/`POLLHUP` на stdin-у **не гаси** чвор — само се престаје са слушањем stdin-а (чворови у позадини). |
| Д10 | `fail` = „замрзнуто" стање: нема слања (ни одговора, ни `LEAVE`-а осим кад је тражен `leave`), нема `heartbeat++`, нема `failure_check`-а; долазни датаграми се и даље читају и merge-ују. `recover` враћа рад. `leave` има предност над `fail`. |
| Д11 | Тајмери: `next_gossip_at += T_GOSSIP`, али ако чвор касни више од једног периода, `next_gossip_at = now + T_GOSSIP` (без налета рунди после застоја). `failure_check` се зове бар једном по рунди. |
| Д12 | `--loss` важи за **свако** слање (`GOSSIP`, `REPLY`, `JOIN`, `LEAVE`) и примењује се у `node_send()`, не у `net.c`. Одбачено због губитка се броји у `dropped_loss`, а не у „послато". |
| Д13 | `leave` и `SIGINT`/`SIGTERM` = уредан `LEAVE` па излаз (код 0). `quit` = излаз **без** `LEAVE`-а (симулира пад, али уредно ослобађа ресурсе — користан за Valgrind/ASan). |
| Д14 | Табела пуна: ако постоји `DEAD`/`LEFT` запис, уклања се најстарији (најмањи `last_update_ms`) и нови се уписује; иначе се нови одбацује уз `WARN` и `dropped_table_full++`. |
| Д15 | Узорак за слање (`mem_sample`): `self` је увек први; ако остали не стану у `MAX_ENTRIES_MSG - 1`, бира се насумичан подскуп (нови за сваког суседа), уз приоритет не-`DEAD` записима. `LEFT` записи се шаљу (иначе се `LEAVE` не би ширио даље од `FANOUT` суседа). |
| Д16 | **Формат излаза CLI-ја.** `list`: први ред заглавље (латиничне колоне, због поравнања и скрипти), затим по један ред по члану (укључујући себе) сортиран по ID-у: 6 колона раздвојених размацима `ID ROLE ADDR STATE HB SILENCE`; последњи ред `# total=N alive=a suspect=s dead=d left=l`. `stats`: редови `кључ вредност`, последњи ред `# end`. Сваки вишередни излаз се завршава редом који почиње са `#`. Једноредне команде одговарају са `OK …` или `ERR …`. |
| Д17 | Излазни кодови: `0` уредно, `1` грешка током рада, `2` погрешни аргументи, `3` seed недоступан после 10 покушаја. |
| Д18 | Сваки прелаз стања члана логује се на `INFO` у истом формату: `member <id> <ROLE>: <ОД> -> <НА> (silence 5.2s)`, где су `ОД`/`НА` ∈ `NEW`, `ALIVE`, `SUSPECT`, `DEAD`, `LEFT`, `REMOVED`. Интеграциони тестови мере време детекције управо из ових редова. Једна помоћна функција (`mem_log_transition`) се користи свуда. |

## Тим и организација рада

Два developer-а, подела **по фајловима** (један фајл = један власник, па нема сукоба при merge-у). Модули комуницирају само преко заглавља из спецификације (§10) — уговори су горе.

| | **Dev A — Core: подаци, протокол, детектор** | **Dev B — Runtime: петља, gossip, покретање** |
| --- | --- | --- |
| Фајлови | `Makefile`, `.github/`, `include/common.h`, `membership.*`, `proto.*`, `net.*`, `failure.*`, `cli.*`, `tests/test_*.c`, `tests/integration/lib.sh` + `s1–s4, s7, s8` | `util.*`, `node.*`, `gossip.*`, `main.c`, `scripts/*`, `tests/integration/s5, s6`, `docs/RESULTS.md`, `docs/DEMO.md` |
| Одговоран за | исправност табеле и merge-а, формат поруке, детекцију испада, команде, квалитет кода | покретање, петљу и тајмере, gossip/JOIN/LEAVE, `--loss`, скрипте, мерења, демо |
| Issue-и | [`dev-A`](../../issues?q=is%3Aissue+label%3Adev-A) | [`dev-B`](../../issues?q=is%3Aissue+label%3Adev-B) |

Заједнички: `README.md`, `docs/REPORT.md` (води Dev A). Измена `common.h` ради се малим, посебним PR-ом који други dev одмах прегледа.

**Где су задаци:** сваки задатак је GitHub issue са чеклистом и критеријумима прихватања; групе су **Milestones** `Фаза 1…8` (из §14 спецификације). Преглед зависности и критичног пута је у issue-у **Roadmap**.

- **`main` увек пролази** `make`, `make test` и `make test SAN=1`. Нико не гура директно на `main` (осим почетног скелета у #1).
- **Гране:** `feat/<issue>-<кратко>` (нпр. `feat/3-membership`), `fix/…`, `docs/…`, `test/…`.
- **Комити:** [Conventional Commits](https://www.conventionalcommits.org/) на енглеском — `feat(membership): sorted insert`, `test(proto): golden vector`.
- **Pull request:** један issue = један (или неколико малих) PR-ова, `Closes #N` у опису, мањи од ~400 линија где се може, **један одобрен преглед од другог dev-а**, squash merge.
- **Header-first:** власник модула гура `.h` са коначним потписима у првом дану, а имплементација следи — тако други може да пише против њега.
- **Stub правило:** ако ти треба симбол из туђег фајла који још не постоји, остави минимални stub у том фајлу са коментаром `/* STUB until #N */`; власник га замењује целом имплементацијом.
- **Промена уговора** (формат поруке, потписи, Д-одлуке) = измена овог README-а у истом PR-у + коментар у погођеним issue-има.
- **Definition of Done:** компајлира се без упозорења (`-Wall -Wextra -Wpedantic -Werror`); `make test` и `make test SAN=1` зелени; нема нових Valgrind/ASan налаза; сви редови чеклисте у issue-у штиклирани; ажурирана документација ако се променио уговор.
- **Језик:** код, идентификатори, логови и комит поруке — енглески; README, issue-и и документација — српски.

## Ван обима, ограничења, проширења

**Ван обима:** трајно складиштење, шифровање/аутентификација, NAT пролаз, прави рад производних машина.

**Позната ограничења** (прихваћена дизајном; документују се у извештају):

- Чвор проглашен `DEAD` оживљава **само** већом инкарнацијом (§7.3) — мрежна подела дужа од `T_FAIL` се не залечи без рестарта.
- Инкарнација у секундама (Д5); нема аутентификације — било ко може да лажира запис.
- Само IPv4, максимално `MAX_NODES = 64` чвора (константа је прошириво).

**Проширења (опционо):** SWIM (директан `PING`, индиректан `PING-REQ`) за мање лажних аларма; „дигест" (хеш табеле) да се избегне слање целог списка; вишенитна верзија (`pthread` + `mutex`); IPv6 и DNS имена; праћење „терета" станица (нпр. температура пећнице) као корисног терета који се шири истим gossip-ом.
